# AGENTS.md

FlatifyCSS is a flat design CSS framework (Sass source, compiled to CSS and a small JS file) with a Docusaurus docs site in `website/`. It is a one person project by Amir M. Mohamadi, MIT licensed. Docs live at https://flatifycss.amimomo.me, the React version is a separate repo (`react-flatifycss`).

## Commands

Package manager is Bun, there are two separate installs (root and `website/`).

```bash
bun install                    # root, build tools
bun run build                  # scss + js into dist/ (does NOT bump the version)
bun run watch                  # dev build on change
bunx gulp release --type patch # bump version in package.json, scss/flatify.scss, js/flatify.js, then build
(cd website && bun install)               # docs dependencies
bun run docs:start                          # docs dev server
bun run docs:build                          # docs production build, also fails on broken links
```

There is no test suite. The checks are: `bun run build` succeeds, the docs build succeeds (it throws on broken links), and `dist/` only changes where you meant it to.

## Layout

- `scss/` Sass source. `_config.scss` holds every setting and its default. `flatify.scss` is the entry. Folders: `components/`, `content/`, `forms/`, `helpers/`.
- `js/` optional behavior (accordion, alert, dropdown, modal, tabs, show password, truncate). `js/config.json` holds the JS options.
- `dist/` compiled output, committed on purpose (npm and CDN serve it). Rebuilt by gulp, never edit by hand. `dist/css/flatify-rtl*.css` are generated copies of the main files for old v1 links, keep them until v3.
- `website/docs/**.mdx` documentation pages, `website/blog/` news, `website/static/` assets.
- `website/static/llms.txt` is generated by `website/scripts/generate-llms.js` on every docs build. Do not edit it by hand, change the docs page titles or first paragraphs instead.

## Rules that are easy to break

- **Do not upgrade `sass`, `autoprefixer` or `cssnano` casually.** They are pinned (sass 1.78, autoprefixer 10.4.0, cssnano 5) so the compiled CSS stays the same. After any tooling change, rebuild and diff `dist/css/flatify.css` against the committed one, only the version banner and intended changes should differ.
- The SCSS still uses `@import` and global functions. Do not convert to `@use` as a side task, it changes output.
- Every Sass setting needs `!default`. CSS variables are prefixed `--flatify__`.
- Components use `em` units, so size is controlled by `font-size`. Use CSS logical properties (`inline`, `start`, `end`) instead of left/right so RTL keeps working.
- Interactive behavior is hooked by class and `data-*` attributes listed on `website/docs/overview/javascript.mdx`. Update that page when you add or rename one.
- When you add or change a Sass variable, CSS variable or helper class, update the docs page for it. Values in doc tables must come from `scss/_config.scss` or the compiled CSS, never from memory.

## Docs conventions

- MDX 3 (Docusaurus 3). Use `className`, not `class`, in JSX. Admonitions are `:::info`, `:::tip`, `:::warning`, `:::danger`.
- Live previews use `<PreviewBox children='...full html...' />` and load the **released** CSS from jsDelivr (`flatifycss@2`), not the local build. A preview will not show an unreleased change.
- Page shape: short intro, preview, titled code block, then a "Customization" section with a variable table.
- Sidebar order comes from `sidebar_position` in frontmatter and `_category_.json`. Keep positions unique inside a folder.
- Internal links start with `/docs/...`. A broken link fails the build.
- Some files use CRLF line endings (`composer.json`, `docs/overview/development.mdx`, several `website/src/components/**`). Keep the existing line endings when you edit them.

## Writing style

The docs are written by hand in a friendly, plain voice. When you fix or add text:

- Fix errors, do not rewrite pages. Keep the author's voice.
- Use "you" for the reader and "I" for the author. Avoid "we", "our" and "the team", this is a personal project.
- No em dashes or en dashes. No marketing words ("seamless", "powerful", "leverage"). Do not open with a definition.
- Do not invent facts, numbers or dates. Measure sizes, check versions.

## Releases

Releasing is a human decision. Do not tag, publish or push. A patch release is `bunx gulp release --type patch`, then commit and tag by hand. Add notes to `CHANGELOG.md` under `Unreleased` for user visible changes.
